# 金山系资讯采集系统 —— 总调度器与汇总实施方案

> **状态：已实施**
>
> 本文档是「总调度器 + 数据汇总 + 产物标准化」阶段的实施方案（下文称 M1），
> 覆盖从采集器驱动到 `latest.json` 产出的完整链路，为后续对接 WPS 多维表格（M2）提供数据源。


---

## 1. 背景与目标

### 1.1 背景

当前 21 个采集器各自独立运行，暴露三个问题：

1. **无统一入口**：缺少一键运行所有采集器的方式，每日需逐个手动执行
2. **批次堆积**：每次运行生成 `{source}_{YYYYMMDD}_{HHMMSS}` 新批次，同一天多次运行产生多个批次，pipeline 全量加载后再去重，成本集中在重复数据上（实测 8/5 加载 121 条、去重后仅 34 条）
3. **结果不可直接消费**：没有统一的、可被下游（简报、多维表格）直接消费的主产物文件

### 1.2 目标

- **M1（本方案）**：总调度器并发驱动全部采集器 → 批次目录生命周期管理 → 汇总（过滤/去重/排序）→ 产出标准化产物（`latest.json`、附件归集、简报、运行报告）
- **M2（后续）**：将 `latest.json` 对接 WPS 多维表格，按"一天一行"组织（日期 | 简报 | 附件 | 源状态 | 统计）
- **M3（后续）**：定时化、增量采集、历史归档、并发优化

本方案只覆盖 M1，M2/M3 在文末给出概要规划，不展开设计。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ main.py (python -m scheduler.main, CLI 入口)                  │
│  registry: 解析 config.COLLECTORS → 启用的源清单               │
│  orchestrator: 编排六步主流程                                  │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ① 并发采集 (ThreadPoolExecutor + subprocess)                  │
│    每个源: python -m collectors.{code}.crawler                │
│    env 注入: BATCH_DIR                                        │
│    运行前清空该源 _latest 批次目录                              │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ② 汇总 (复用 DataPipeline)                                    │
│    只加载各源 _latest 批次 → 时间过滤 → 去重(L1+L2) → 排序      │
│ ③ 附件归集: 保留记录的 PDF → output/latest_attachments/        │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ④ latest.json (主产物, 含 sources 状态 + stats + items)       │
│ ⑤ 简报 md (generate_briefing, 可跳过)                        │
│ ⑥ 运行报告 + 日志                                            │
└─────────────────────────────────────────────────────────────┘
                           ▼
                    (M2 对接 WPS 多维表格)
```

数据流单向：调度器只负责"起采集 + 收状态"，汇总逻辑复用现有 `pipeline`，不重写。

## 3. M1 详细设计

### 3.1 模块结构

```
scheduler/
  __init__.py
  registry.py        # 从 config.COLLECTORS 解析 enabled=True 的源
  orchestrator.py    # 主流程编排: 采集 → 汇总 → 附件归集 → 简报 → 报告
  result.py          # CrawlerResult / RunSummary 数据结构
  main.py            # CLI 入口 (argparse)
```

入口为 `python -m scheduler.main`，**不创建根目录 `main.py`**（项目约定：README 引用的 `main.py` 不存在且不创建）。

#### 3.1.1 源发现与可扩展性（增添/去除采集器）

调度器从 `config.COLLECTORS` 中 `enabled=True` 的条目自动发现源。当前启用 **16 个**：cninfo / hkex / kingsoft_ir / kingsoft_office_ir / weibo / stcn / kr36 / yicai / cls / huxiu / eastmoney / xueqiu / zhidx / gamelook / gamersky / ali213（collectors 下共 17 个 crawler 模块，其中 `wind` 已写代码但 `enabled=False`）。

**增添采集器（两步）**：

1. `config/settings.py` 的 COLLECTORS 新增一条目（`enabled: True`）
2. 新建 `collectors/{code}/crawler.py`，满足三条契约：
   - 继承 `BaseCrawler`（获得 `BATCH_DIR` 注入与标准 `save()`）
   - 模块路径与 config key 一致（`collectors/{code}/crawler.py`）
   - 含 `if __name__ == '__main__'` 入口（供 `python -m` 调用）

**去除采集器（一步）**：config 中 `enabled: False` 即可，代码保留便于恢复。

**registry 校验**：启动时对每个 `enabled=True` 的源校验模块存在性，缺失则列出清单并报错退出，防止 config code 写错时静默失败。

> **xueqiu 说明**：当前 `enabled=True`，但按既定要求暂不为其做特殊适配，遵循通用契约处理（若运行异常，按标准失败提示标出）。若全量运行不希望包含雪球，将 `enabled` 置 `False` 一行即可——这正是"去除采集器"的体现。

### 3.2 采集驱动：subprocess + 线程池

#### 技术依据

- 12+ 个采集器使用 Playwright 同步 API，无法走 asyncio
- 每个 Chromium 实例约占 200~400MB 内存，全并发有打爆内存和触发反爬的风险
- **选型：`ThreadPoolExecutor`，默认并发 4**（`--max-workers` 可调）

#### 执行方式

每个采集器在独立 subprocess 中运行，命令为：

```
[sys.executable, "-m", f"collectors.{code}.crawler"]
```

cwd 固定为项目根目录，继承父进程 env 并注入以下变量：

| 环境变量 | 值 | 用途 |
|---|---|---|
| `BATCH_DIR` | `output/data/{code}/{YYYY}/{MM}/{DD}/{code}_{YYYYMMDD}_latest` | 批次目录注入（见 3.3） |

选择 subprocess 而非进程内实例化的理由：

1. **零适配**：采集器无需修改运行入口，`base.py` 一处改造即可全部生效
2. **进程隔离**：Chromium 崩溃不影响调度器及其他采集器
3. **汇总从文件加载**：调度器不依赖采集器返回的内存对象，subprocess 不损失信息

> V2 优化方向（M3）：改为 importlib 适配层实例化，配合进程池、增量采集。
> 本方案保留 `CrawlerResult` 数据结构，届时不破坏接口。

#### 3.2.1 时间窗口职责边界

**调度器不注入 `{CODE}_HOURS_WINDOW`**，时间窗口由各采集器自行负责：

- 采集器 `main()` 中个别非 24h 默认值（如 huxiu 1000h、cninfo 500h）是调试期临时改动，后续统一规范为 24h；调度器不关注采集器内部的时间过滤
- 调度器只在自己这一层做时间过滤：汇总阶段以 **24h 窗口统一兜底**（见 3.4.1），保证进入 `latest.json` 的数据不超过 24h 范围
- `enable_summary` 不需要注入：采集器构造函数默认从 config 读取该配置

> 备注：在采集器完成 24h 规范前，个别源单次运行仍会超采（PDF 下载增多、耗时变长）。调试期可接受；如遇运行时间过长，用 `--sources` 子集运行规避。

#### 3.2.2 状态判定与失败语义

| 判定条件 | 源状态 |
|---|---|
| exit code 0 且批次 JSON 存在 | `ok`，count 从 JSON 读取 |
| exit code 非 0 | `failed`，error 取 stderr 尾部（截断） |
| exit code 0 但 JSON 不存在 | `warning`（未产出数据） |

**失败语义**（贯穿全链路）：

- 单源失败 → 标记 `failed` 继续汇总，不中断其他源
- 汇总失败 → 整个任务失败，原始批次数据保留供排查
- 简报/附件失败 → 记为 warning，不阻塞主产物

#### 3.2.3 超时兜底与失败提示

- 单源 subprocess 设超时上限（默认 **5 分钟**，超过则 kill 并标记 `timeout`），防止单个采集器卡死拖累整体。超时值作为配置项放入 `config/settings.py`
- 采集失败时给出清晰提示：控制台与运行报告均输出 `[FAILED] {source}: 退出码 {code}，错误: {stderr 尾部摘要}`，并指引该源日志文件路径 `output/logs/collectors/{source}/`

#### 3.2.4 Windows 编码处理

Windows 下采集器 stdout/stderr 中文输出存在 GBK/UTF-8 混排风险。subprocess 捕获输出时统一按 UTF-8 解码（`errors="replace"`），避免解码异常导致调度器崩溃。

### 3.3 批次目录管理：固定目录 + 覆盖写

#### 3.3.1 现状与问题

当前批次目录：`output/data/{source}/{YYYY}/{MM}/{DD}/{source}_{YYYYMMDD}_{HHMMSS}/`

- 每次运行生成带时间戳的新批次，同一天多次运行 = 多个批次
- pipeline 按日期全量加载 → 重复处理、磁盘堆积

#### 3.3.2 目标形态

批次名固定为 `{source}_{YYYYMMDD}_latest`，同一天多次运行写入**同一目录**，覆盖写不堆积：

```
output/data/{source}/{YYYY}/{MM}/{DD}/{source}_{YYYYMMDD}_latest/
    ├── {source}_{YYYYMMDD}_latest.json
    ├── contents/ann_000.txt
    └── pdfs/xxx.pdf
```

**目录层级保持现状不动**（保留 `{YYYY}/{MM}/{DD}` 三级）。压扁层级收益有限，且涉及 pipeline 加载逻辑与历史数据兼容，列为 M3 优化项。

#### 3.3.3 实施方式（已核实）

**已核实的约束**：collectors 下 17 个 crawler 模块全部在 `fetch()` 内覆盖 `self._batch_dir`（代码形态一致），仅在 `base.py` 注入不会生效。wind 模块同样加保护，未来启用即受益。

改动清单：

| 改动点 | 内容 |
|---|---|
| `collectors/base.py` `__init__` | 读 `BATCH_DIR` 环境变量 → 设置 `self._batch_dir`（约 3 行） |
| 17 个 crawler 模块 `fetch()` | `self._batch_dir = f"{...}"` 改为 `if not self._batch_dir: self._batch_dir = f"{...}"`（条件保护，每处 1 行） |

条件保护语义完全向后兼容：不注入 `BATCH_DIR` 时行为与现状一致（独立运行采集器不受影响）；注入时采用调度器指定目录。

**hkex 已核实**：仅 2 处赋值。L458（`fetch()` 主流程开头，无条件赋值，最终生效）需加条件保护；L172（`_fetch_single_stock` 内）已带 `if not self._batch_dir:` 保护，无需改动。注意 L458 赋值后紧跟 `pdf_processor.set_download_dir()`（L463-465）：改造后当 `_batch_dir` 已由外部注入时，pdf 目录须从注入目录推导（`os.path.join(self._batch_dir, "pdfs")`），保证 PDF 仍落盘在注入批次内。

> 说明：`content_ref` 与 `pdf_path` 存的是相对批次目录的相对路径，目录调整只影响路径拼装，不影响已存 JSON 的引用关系。已确认下游（pipeline/简报）不消费 `load_content_from_ref()` 正文，`_latest` 覆盖写安全。

#### 3.3.4 清理策略

- 调度器在启动某源前，删除该源对应的 `_latest` 批次目录（先清后写）
- 接受取舍：调试期若中途崩溃，当天该源数据可能丢失（调试数据无价值，可接受）
- 历史遗留的时间戳批次（调试期堆积）**不自动清理**，V1 保留不动，由 M3 的归档功能统一处理

### 3.4 汇总与产物

#### 3.4.1 汇总流程

复用现有 `DataPipeline`，加载范围改为**只扫各源的 `_latest` 目录**（避开历史堆积）：

```
加载 _latest 批次 → NewsItem 解析 → 时间过滤（24h 统一） → 去重（L1 + L2增强） → 排序
```

#### 3.4.2 主产物 `output/latest.json`

```json
{
  "schema_version": 1,
  "run_id": "20260817_093000",
  "date": "2026-08-17",
  "generated_at": "2026-08-17T09:30:00+08:00",
  "sources": {
    "cninfo":  {"status": "ok",      "count": 12, "duration_s": 34.2, "error": null},
    "weibo":   {"status": "failed",  "count": 0,  "duration_s": 8.1,  "error": "cookies expired"}
  },
  "stats": {
    "raw": 98, "after_time": 75, "after_dedup": 34, "attachments": 12
  },
  "items": [
    {
      "title": "...",
      "url": "...",
      "publish_time": "2026-08-17",
      "source_code": "cninfo",
      "credibility_tag": "【官方公告】",
      "category": "资本动态",
      "summary": "...",
      "pdf_path": "cninfo_xxx.pdf",
      "fetch_time": "..."
    }
  ]
}
```

要点：

- `sources` 状态是必备字段：简报内容偏少时，可区分"当天确实无新闻"与"采集器失败"
- `items` 为去重排序后的最终结果，`pdf_path` 指向归集后的附件目录（见 3.4.3）
- 该文件是 M2 对接多维表格的唯一数据源

#### 3.4.3 附件归集 `output/latest_attachments/`

- 收集去重后保留记录中 `raw_data.pdf_path` 指向的 PDF，拷贝到 `output/latest_attachments/`（扁平命名，防重名加前缀）
- 更新 `latest.json` 中对应 `pdf_path` 为归集后相对路径
- 每次运行清空重建该目录
- **只归集 PDF**：txt 是 PDF 解析产物，无独立证据价值，不进入归集链路
- 媒体类采集器无 PDF，跳过

该目录与 `latest.json` 一起构成 M2 的附件数据源。

#### 3.4.4 简报

复用现有 `generate_briefing`，输出到 `output/briefings/{YYYY}/{MM}/briefing_{YYYYMMDD}.md`。

- 同一天多次运行覆盖写同名简报（与"当天刷新"语义一致）
- `--no-briefing` 可跳过

#### 3.4.5 运行报告 `output/reports/run_{YYYYMMDD_HHMMSS}.json`

记录每次运行的完整状态：每源 `status / count / duration / error / stdout 尾部`，以及汇总统计。调试期一眼定位失败源；该信息未来直接映射到多维表格的"源状态"字段。

#### 3.4.6 日志

- 调度器日志：`output/logs/scheduler/{YYYY-MM-DD}.log`
- 采集器日志沿用各自现有机制（`output/logs/collectors/{source}/`），两条线不冲突
- 默认 INFO；`-v` 打开 DEBUG（含每条记录、去重命中明细）

### 3.5 去重增强（L2）

#### 分层模型

| 层级 | 方法 | 范围 |
|---|---|---|
| L1 | URL 精确匹配 | 必做（已有） |
| L2 | 归一化标题匹配 | 增强（本次） |
| L3 | 字符相似度（阈值 0.8 起） | 后续推进（M2+） |
| L4 | 语义相似度（embedding） | 延后，视 L2/L3 效果决定 |

#### L2 增强内容

现有归一化仅去除标点与空白。本次增加：

1. **繁简转换**：引入 `opencc-python-reimplemented`（纯 Python 实现，无 C 依赖），标题统一转简体后比较，解决"金山軟件 vs 金山软件"
2. **去通用前后缀**：剥离 "快讯:" / "独家|" / "【xxx】" / "来源:xxx" 等通用修饰，解决 cls 截断标题与 eastmoney 完整标题匹配不上的已知遗留问题
3. 初始前缀/后缀规则集在实施时定义，回测后扩充

**同事件不同角度（如"业绩发布"与"业绩解读"）不做去重**；跨可信度同组（官方 + 媒体）保留最高可信度。

#### 回测方案

- 样本：现有历史批次（8 月堆积数据，含大量重复，天然适合）
- 流程：用新去重逻辑跑历史数据 → 输出疑似重复对清单 → 人工抽查误杀率（目标 < 5%）→ 校准规则/阈值后固化
- 产出：回测报告 + 定稿规则集，随 M1 交付

### 3.6 CLI 设计

```
python -m scheduler.main [选项]

--sources cninfo,hkex    仅运行指定源（逗号分隔），默认全部启用源
--max-workers 4          并发采集数，默认 4
--dry-run                只采集不汇总（与 --skip-collect 互斥）
--skip-collect           只汇总不采集（重跑汇总/调去重）
--no-briefing            跳过简报生成
--list-sources           打印启用源清单后退出，不运行
-v / --verbose           打开 DEBUG 日志
```

语义约定：

- **`--sources` 子集运行**：`latest.json` 只包含本次运行的源，且覆盖写主产物。调试期注意子集运行会覆盖全量结果（可用 `--dry-run` 或 `--skip-collect` 组合规避）
- **`--skip-collect`**：从各源 `_latest` 目录加载上次运行数据重跑汇总，用于调去重阈值
- **`--dry-run`**：验证采集器本身是否工作

## 5. 风险与待确认事项

### 5.1 已核实并纳入设计

| 事项 | 结论 |
|---|---|
| 采集器 `_batch_dir` 覆盖 | 17 个 crawler 模块均需条件保护（含未启用的 wind）；hkex 实际只需改 1 处（L458），详见 3.3.3 |
| 时间窗口默认值不一致 | 属调试期遗留，后续统一规范为 24h；调度器不注入，由汇总层 24h 过滤兜底 |
| 目录层级过深 | V1 保留现状，压扁列为 M3 |
| 历史批次堆积 | V1 只清 `_latest`，历史遗留不动 |

### 5.2 遗留决策点

| # | 事项 | 当前倾向 | 说明 |
|---|---|---|---|
| 1 | 单源超时上限 | 5 分钟 | 超过则 kill 并标 `timeout`，失败提示含退出码与错误摘要 |
| 2 | 汇总时间过滤窗口 | 24h 统一 | 与 config 各源 `hours_window=24` 对齐；`TIME_FILTER.default_hours` 由 48 改为 24 |
| 3 | `--sources` 覆盖写主产物 | 接受 | 调试期注意子集运行覆盖全量结果 |

## 附：M2/M3 概要规划

### M2 —— WPS 多维表格同步（后续阶段）

- 结构：一天一行（日期 | 简报内容 | 附件 | 源状态 | 统计 | 采集时间）
- 同步语义：按日期 upsert，天然幂等，当天多次运行 = 刷新当天行
- 附件方案待实测后定（A 全部挂 / B 分字段 / C zip 打包）
- 对接层独立模块，只消费 `latest.json` + `latest_attachments/`，同步失败不影响本地产物

### M3 —— 定时化与优化（后续阶段）

- 定时化：内置调度或系统计划任务，每日自动运行
- 增量采集：传递上次成功批次时间戳，减少重复抓取
- 历史归档：`_latest` 快照归档到 `output/archive/`
- 目录压扁：`output/data/{source}/{YYYYMMDD}/`
- 并发优化：适配层实例化、按类型分池、动态并发
