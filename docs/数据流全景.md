# 数据流全景

> 从采集器落盘 → 调度器汇总 → 简报/报告 → WPS 多维表格同步，四段完整链路。
> 配套代码：`scheduler/orchestrator.py`、`scheduler/summarizer.py`、`pipeline/__init__.py`、`scheduler/sync_bitable.py`、`scheduler/registry.py`、`models/news.py`、`scheduler/result.py`、`config/settings.py`、`scheduler/briefing.py`。

---

## 0. 总览

```text
config/settings.py (COLLECTORS 启用源)
        │
        ▼
[阶段1 采集 orchestrator.py] ── subprocess 并发 ──▶ output/data/{source}/.../xxx_latest.json
        │                                            (batch JSON + contents/ + pdfs/)
        ▼
[阶段2 汇总 summarizer.py + pipeline] ── 只扫 *_latest.json ──▶ output/latest.json
        │                                                     + output/latest_attachments/*.pdf
        ▼
[阶段3 简报/报告] ──▶ output/briefings/.../briefing_YYYYMMDD.md
                   + output/reports/run_*.json
        ▼
[阶段4 同步 sync_bitable.py] ── 读 latest.json + latest_attachments ──▶ WPS 多维表格（每源一行 upsert，云文档上传附件）
```

## 1. 阶段 1：采集器（模块 C）

**入口**：`python -m scheduler.main` → `orchestrator.run(args)`。

**做了什么**：

1. `registry.resolve_sources()` 从 `config/settings.py` 的 `COLLECTORS` 里筛出 `enabled=True` 的源，每个源对应 `collectors/{code}/crawler.py` 一个模块（`validate_sources` 先校验文件存在）。
2. `collect()` 用 `ThreadPoolExecutor` **4 并发**（`--max-workers` 可调）跑 subprocess：`python -m collectors.{code}.crawler`，**单源超时 5 分钟 kill**（`SCHEDULER.timeout_seconds`）。
3. 每个源跑之前，把批次目录通过环境变量 `BATCH_DIR` 注入，并**先清后写**（`_clean_latest` 删旧 `_latest` 批次，防止残留）。

**落盘位置**：

```text
output/data/{source_code}/{YYYY}/{MM}/{DD}/{source_code}_{YYYYMMDD}_latest/
  ├─ {source_code}_{YYYYMMDD}_latest.json   ← 批次主文件
  ├─ contents/ann_000.txt                   ← 每条正文全文（不内联进 JSON，通过 content_ref 引用）
  └─ pdfs/688111_xxxx.pdf                   ← 公告原文 PDF（巨潮/IR 类源才有）
```

**批次 JSON 格式**（真实样例，`weibo_20260818_latest.json`）：

```json
{
  "source": "微博", "source_code": "weibo",
  "fetch_time": "2026-08-18T15:29:23",
  "count": 3,
  "items": [{
    "title": "风筝载愿，金鱼祈福。#剑网3十七周年#...",
    "date": "2026-08-18",
    "url": "https://weibo.com/...",
    "source_code": "weibo",
    "credibility_tag": "【官方资讯】",        // 官方公告/官方资讯/媒体报道
    "category": "产品动态",                   // 5 类，采集器内关键词自动打标
    "publish_time": "2026-08-18T00:00:00",
    "summary": "《剑网3》十七周年主题活动正式公布。...",  // AI 摘要（采集阶段已生成）
    "summary_generated_at": "2026-08-18T15:29:23",         // 摘要生成时间
    "content_ref": "contents/ann_000.txt",    // 正文全文引用
    "raw_data": { "pdf_path": "pdfs\\688111_xxx.pdf", ... }
  }]
}
```

**注意**：`summary_generated_at` 为新增字段，记录 AI 摘要生成的具体时间。

**运行状态判定**（`result.py`，写入 `sources` 段）：

| `failed` | exit 非 0 |
| `warning` | exit 0 但未产出 JSON |

## 2. 阶段 2：汇总与主产物（模块 D，核心）

**入口**：orchestrator 里 `from scheduler.summarizer import run_summary` → `run_summary(source_codes, results, logger)`。

**取用了哪些文件**：`load_latest_batches()` **只扫各源 `*_latest.json`**（`find_latest_batch_json` 按文件名倒序取最新），刻意避开历史堆积批次。加载为 `NewsItem`，并在 `raw_data` 里附加 `_batch_dir` / `_fetch_time`（供附件归集和 latest.json 用）。

**做了什么，按顺序 7 步**：

| 步骤 | 逻辑 | 落点 |
|---|---|---|
| ① 时间过滤 | `DataPipeline.filter_by_time`：`publish_time >= now - 24h`（`TIME_FILTER.default_hours=24`，注：采集器层各有 `hours_window`，汇总层统一兜底 24h） | 部分采集器（如巨潮、IR官网）时间窗 >24h 有召回结果，汇总层统一按 24h 过滤 |
| ② 去重 | `deduplicate` 两轮：**L1 按 URL** 归并，**L2 按归一化标题**（opencc 繁转简 → 去"快讯/独家"前后缀 → 去标点）；同组保留可信度最高（官方公告 > 官方资讯 > 媒体报道） | `pipeline/__init__.py` |
| ③ 排序 | `publish_time` 倒序 | |
| ④ 附件归集 | `collect_attachments`：清空重建 `output/latest_attachments/`，把 PDF 扁平拷贝为 `{source_code}_{原文件名}`（重名加序号），并把 item 的 `pdf_path` 更新为 `latest_attachments/xxx.pdf` | |
| ⑤ 状态汇总 | 各源采集结果并入 `RunSummary.sources`（缺省源标记 `pending`） | |
| ⑥ 写主产物 | `LATEST_JSON.write_text(...)` | `output/latest.json` |
| ⑦ 保留去重后 NewsItem | 供阶段 3 简报生成用（`summary.news_items`） | 不进 latest.json |

**主产物 `output/latest.json` 结构**（`result.py` + `_to_latest_item`）：

```json
{
  "schema_version": 1,
  "run_id": "20260818_152900",
  "date": "2026-08-18",
  "generated_at": "2026-08-18T15:29:00",
  "sources": { "cninfo": {"status":"ok","count":3,"duration_s":12.3,"error":null}, ... },
  "stats": { "raw": 18, "after_time": 2, "after_dedup": 2, "attachments": 3 },
  "items": [{
    "title": "...", "url": "...",
    "publish_time": "...", "source_code": "cninfo",
    "credibility_tag": "【官方公告】", "category": "资本动态",
    "summary": "...", "pdf_path": "latest_attachments/cninfo_xxx.pdf",
    "content_ref": "contents/ann_000.txt",
    "batch_dir": "output/data/cninfo/2026/08/18/cninfo_20260818_latest",
    "fetch_time": "2026-08-18T15:29:23"
  }]
}
```

**新增字段**：
- `content_ref`：正文文件相对 batch_dir 路径（下游可读取全文）
- `batch_dir`：批次目录绝对路径（定位 content_ref/pdf_path 用）
- `fetch_time`：采集时间（区分同一天多次运行）

**注意**：`raw / after_time / after_dedup` 三个数字的落差是"过滤/去重"的客观记录，不是 bug——`raw=18 / after_time=2` 是 24h 时间窗过滤的正常结果（部分采集器时间窗 >24h，召回结果在调度器处被 24h 时间窗滤掉）。

## 3. 阶段 3：简报与运行报告（模块 E）

- **简报**：`generate_briefing(summary.news_items)` 用去重后的 `NewsItem` 列表生成 Markdown → `output/briefings/{YYYY}/{MM}/briefing_{YYYYMMDD}.md`（`DailyBriefing.to_markdown`，按 5 类分组 + 概览 + 重点关注）。`--no-briefing` 可跳过。入口也可单独运行：`python -m pipeline`。
- **运行报告**：`write_run_report` → `output/reports/run_{YYYYMMDD_HHMMSS}.json`（每源详细状态 + 退出码 + stdout/stderr 尾部）。
- **日志**：`output/logs/scheduler/{日期}.log`。

**简报生成细节**（`models/news.py:DailyBriefing.to_markdown`）：
- 按 5 类固定顺序输出：资本动态 → 产品动态 → 市场&政企合作 → 活动IP → 人事&其他声明
- 每条含：可信度标签 + 标题、来源、时间、原文链接、摘要
- 末尾有"重点关注"前 5 条汇总

## 4. 阶段 4：WPS 多维表格同步（模块 F，M2）

**入口**两种：
- `--sync-bitable`：汇总完紧接着同步（orchestrator 内调用）
- `--sync-only`：只同步，读现有 `latest.json`，不采集不汇总
- `--sync-dry-run`：仅打印待写入记录，不调用 API（可配合以上两者）

**消费什么文件**：`load_latest()` 只读两样——`output/latest.json` + `output/latest_attachments/` 目录下的 PDF。

**重大变更（vs 旧版方案）**：**附件改为云文档三步上传**，不再尝试直接写多维表格"附件"字段（开放平台服务端无素材库上传接口，"附件"字段无法程序化写入）。现方案：
1. **有 PDF** → 上传云文档拿到 `link_url`，构造 cloud 附件结构体（source=cloud, uploadId=短链接后缀），写入"附件"字段（原生卡片渲染 + 在线预览）
2. **无 PDF** → 读正文（`content_ref` + `batch_dir` 定位），转 txt 上传云文档，同样写"附件"字段
3. **同时**把 `link_url` 写入"附件链接"字段（文本备份，便于复制/归档）

**组装**（`build_record` → 每采集器一行）：

| 列 | 值来源 |
|---|---|
| 信息源 | `COLLECTORS[code].name`（配置中文名） |
| 总结 | **L1 清洗**：5 类分组 + 组内可信度/时间排序 + 编号 + 摘要缩进 |
| 附件 | **云文档上传结构体数组**（PDF + 正文 txt 均上传），写入"附件"字段（卡片渲染） |
| 附件链接 | 所有 `link_url` 换行拼接，写入"附件链接"字段（文本备份） |
| 原始链接 | 该源全部条目 url，每条一行 |
| 分类 | 全部列出，按命中条数降序（条数相同按 `CATEGORIES` 定义顺序） |
| 可信度 | `COLLECTORS[code].credibility` 剥掉【】后写入 SingleSelect（官方公告/官方资讯/媒体报道） |

**鉴权链**：`BitableClient` —— 用户级 OAuth token 存 `output/wps_token.json`（内存缓存 → 文件 → refresh 自动刷新）；每次请求带 `Authorization: Bearer` + `KSO-1` 签名头（HMAC-SHA256 拼接：`KSO-1` + Method + URI + ContentType + KsoDate + sha256(body)）。

**upsert 语义**：`list_records` 按「信息源」字段过滤查 → 客户端解析「创建时间」字段（表格返回斜杠格式 `2026/08/20 10:58:05`，兼容解析）判断是否**今天** → 查到走 `update_record`（按 record_id 全量覆盖），查不到走 `create_record`。**这就是"手动改过的内容下次同步会被覆盖"的原因**。

**失败语义**：同步失败仅 `logger.error` + 返回非 0，不影响采集/汇总产物。

**配置**（`.env` 覆盖，`config/settings.py:BITABLE`）：
- `WPS_SYNC_ENABLED=1` 启用同步（默认关闭）
- `WPS_APP_ID` / `WPS_APP_KEY` / `WPS_FILE_ID` / `WPS_SHEET_ID` 必填
- `WPS_REDIRECT_URI`（默认 `http://127.0.0.1:8765/callback`）
- Scope：`kso.dbsheet.readwrite,kso.dbsheet.read,kso.drive.readwrite,kso.file.readwrite`

## 7. 关键数据模型变更（`models/news.py`）

- **NewsItem 新增字段**：`summary_generated_at`（摘要生成时间）
- **可信度归一化**：`normalize_credibility()` 统一映射为三值（官方公告/官方资讯/媒体报道），兼容历史复合写法
- **分类清洗**：`from_dict` 自动剥离中文数字前缀（①资本动态 → 资本动态）
- **DailyBriefing**：新增 `generated_at` 默认工厂函数

## 8. 一句话总结整个链路

**采集器各自落盘原始批次（JSON + contents + pdfs）→ 调度器只扫各源 `_latest.json`，统一 24h 过滤 + 双轮去重 + 排序，PDF 归集，产出 `latest.json` → 同步层只消费 `latest.json` + `latest_attachments/`，PDF/正文上传云文档拿链接，组装成每采集器一行 upsert 进 WPS 表格（附件写云文档卡片 + 附件链接文本备份）。** 中间每一层都有独立产物文件，下游只依赖上游的"成品"文件，所以 `--skip-collect` / `--sync-only` 才能单独重跑某一层。
